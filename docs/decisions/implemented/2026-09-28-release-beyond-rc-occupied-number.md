# DR: 正式版不复用已被 rc 占用的版本号

Status: implemented

## Problem

`0.4.4-rc.1` 已于 2026-09-23 发到公共 registry 并挂在 `next` dist-tag 上，是装了 `--tag next` 的用户与宿主侧验证 dsh 0.1.7 兼容性的实际对象。rc 之后又落地了费用 pill 迁入 composer dock 的整块 UI 变更（`5d8a330`，+1088/−823，物理删除右上角 `SessionStatsChip`），改动面与回归风险都超出"rc 之后顺手修几个 bug"的量级。

若正式版沿用 0.4.4 编号，就会出现"0.4.4 正式版内容 ≠ 0.4.4-rc.1"：rc 阶段积累的兼容性结论无法平移到正式版（用户验证过的代码根本不在正式版里），用户报障时也无从判断自己装的是 rc 面还是 pill 面，同一版本号对应两份不同行为。

## Decision

正式版使用未被占用的新编号 `0.4.5`，`0.4.4-rc.1` 的编号就此永久退役。两条准则：

1. **编号一旦以预发布形态（`-rc.N` / `-alpha.N`）进入 registry，其主版本号即视为已消耗**，正式版顺延到下一个未被占用的编号，永不复用。判断基准是 registry 上的已发布版本，不是本地 git tag。
2. **正式版发布后清理 `next` dist-tag**（本次一并清掉早于 latest 的 `dsh-alpha` 遗留标签）。`latest` 已是正式版而 `next` 仍指向更旧的 rc，构成标签指向倒挂，会让用户误以为还有更新的预发布版可选。

## Alternatives considered

- **正式版直接用 0.4.4（rc → final 同号）** —— 这是最常见的惯例，但成立前提是 final 内容与 rc 完全一致；本次 rc 后又改了客户端展示层，验证对象已漂移，同号发布等于让 rc 的验证结论作废还制造同号双面。输。
- **unpublish 掉 `0.4.4-rc.1` 再占回 0.4.4** —— npm 仅开放 72 小时的 unpublish 窗口且要求无人依赖，本包已公开可安装早已出窗；撤回等于永久浪费一个编号，还搭上号被他人抢注的风险，仍不解决同号双面。输。
- **先发 `0.4.5-rc.1` 跑一轮验证再发正式版** —— rc 阶段要验证的宿主 0.1.7 兼容性已在 `0.4.4-rc.1` 上完成；本轮增量集中在客户端展示层，且有 325 行新增测试（`tests/cost-pill.client.spec.tsx`）与被删除组件的测试迁移兜底，再插一轮 rc 只是增加发版延迟。输。

## Consequences

- 换来：每个已发布编号的内容唯一且与其验证记录一一对应；`latest` 装到的必定是"费用 pill dock"这一面，peer 依赖统一为宿主 `^0.1.7-rc.1` 后，`README` 里不带 tag 的安装命令也无需再加说明。
- 代价：版本序列出现 0.4.4 正式版的空洞，`latest` 从 0.4.3 直接跳到 0.4.5，发版说明里需要点明原因；此后每发一轮 rc 都要为正式版预留编号，长期看版本号增速略快于功能节奏。
- 顺带确认：仓库中的 `package-lock.json` 是 pnpm 统一前的遗留物（其 `version` 仍停在 0.4.3、devDeps 仍是 0.1.7-alpha.1），发版不读取它，本次不随版本号同步修改，维持其"被 `files` 白名单排除在 tarball 外"的既有状态。
