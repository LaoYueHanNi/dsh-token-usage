# DR: 配额触发器按额度池聚合（多 key 网关的水位与可用性）

Status: implemented

## Problem

magpie 这类网关把同一供应商的**多个 key** 并列成多张配额卡（每个 key 一份独立额度，互为备份，网关按剩余量智能路由）。面板本身是逐卡正确的，但输入栏的触发器圆圈只读「tier 最细的那一个窗口」——多卡时等于「遇到的第一个窗口」。一个 key 用尽（5 小时剩余 1%）就把整个供应商画成红色，尽管另外两个 key 还有 93%、95%，会话仍然可以照常跑。

这个红色是**语义错误**：它报告的是「某个账号的额度用完了」，而圆圈该回答的是「我现在还能不能用、还剩多少」。同时，简单地改成「多张卡取平均」也不成立——跨供应商平均没有意义（DeepSeek 的 5 小时与 MiniMax 的 5 小时不是同一份额度），且平均会稀释告警（3 个 key 挂 1 个，平均 63% 全绿，用户看不见有个 key 已经死了）。

## Decision

**额度池（pool）成为 wire 协议的一等信息。** `QuotaWindow` 新增可选字段 `pool`：标注该窗口所属的**额度池**——同一池的窗口出自同一供应商、各有独立额度但服务同一份流量，因而可以互换。magpie 适配器按 `provider::name`（供应商路由键 + 展示名）写入 pool：同一供应商的多个 key、多个账号、多个套餐共享一个池；不同供应商永不同池；其余适配器不写 pool（单源，没有可池化之物）。

**套餐不参与池标识**：lite 与 pro 虽是分开计量的两份额度，但网关把两者都当作该供应商的账号，流量在它们之间调度（报告里两张卡的 `lastServedAt` 交替出现）——对圆圈回答的问题（「我还能不能用这个供应商？」）而言，它们就是一份预算。池化衡量的是**可路由性**，不是「额度是不是同一份」。

**触发器读池化后的水位。** 客户端新增 `poolQuotaWindows`：把同一 pool、同一 tier（`other` 窗口另按自身窗口名分组）的窗口合并成一个**池水位**——各窗口剩余份额的**算术平均**；无 pool 的窗口自成一组，余额窗口永不池化（金额不是份额，两个钱包求和/平均都不说明问题）。`quotaPoolSeverityOf` 再按**池内可用性**给这个水位上色：

- **红**：池内窗口**全部**耗尽（剩余 < 20%）——池里确实没有可路由的额度了；
- **黄**：水位本身偏低（均值 ≤ 60%），或**部分**窗口已耗尽而其余仍有量（一个账号死了，池还能服务）；
- **绿**：其余。

单窗口的判定与改造前**逐位等价**（peerCount=1 时直接走原来的 per-window 分档），所以所有单源供应商的观感不变。

面板**保持逐卡明细**（每个 key 一栏自己的百分比），不改形状；只有输入栏的圆圈与它的 tooltip 改为池化语义，tooltip 在池化时点明「N 个额度均值」。

路由组（`group/…`）与裸模型 id 会让 magpie 适配器回退到**全舰队**卡片。此时各供应商的 pool 互不相同，池化自然不发生——每个供应商各算各的，圆圈行为与改造前照旧，正是「无法判断实际请求模型时不做处理」的要求。

## Alternatives considered

- **只取平均（颜色也按平均）** —— 输在稀释告警：3 个 key 挂 1 个，均值 63% 显示全绿，用户直到全挂才发现问题；且「均值的颜色」与「还有 key 可用」这两件事被压成了一个数。
- **取可用性优先（环画当前还能用的最大剩余率）** —— 输在掩盖事实：池里 2 个 key 已死、1 个还剩 95% 时显示绿色，池子的损耗被完全抹掉；且环填充会随网关切换到不同 key 而剧烈跳动，读数不稳。
- **跨供应商平均（不引入 pool，全部窗口一起平均）** —— 输在没有语义：不同厂商的同名窗口不是同一份额度，平均出来的数字不对应任何真实额度；路由组场景下尤其荒谬。
- **同供应商不同套餐分开成池** —— 输在池化衡量的是**可路由性**而非「额度是不是同一份」：网关在 lite 与 pro 两个账号之间调度流量（`lastServedAt` 交替），对「我还能不能用 GLM」而言它们就是一份预算；分开成池会让明明可路由的场景退回「只读第一个窗口」的老毛病。
- **池只按 provider 键（不带展示名）** —— 输在可能把同路由键下的不同展示名（疑似不同站点或不同套餐线）并成一池，池化跨到了并不互通的额度上；带上展示名后，真实网关里同站点的多 key / 多账号仍然同池。
- **服务端（magpie 适配器）直接算出聚合窗口** —— 输在面板要逐卡明细：适配器一聚合就丢掉了「哪个 key 剩多少」，客户端再也画不出分栏；聚合只能是**派生视图**，不能是**替换数据源**。
- **分段环（每个 key 一段弧）** —— 信息量最大，但 14px 的触发器切 3 段已相当拥挤，读数精度与实现复杂度都不划算；留作未来空间。
- **跨供应商也分级（部分供应商耗尽就整体变黄）** —— 输在违背约定：路由组场景下无法判断实际请求落到哪个供应商，整体变黄等于对无关供应商发警报。

## Consequences

- 代价：wire 协议多一个可选字段（`QuotaWindow.pool`），magpie 适配器每张卡多写一个字段；客户端多一层池化派生与一条分级规则；池化 tooltip 多一条文案（中英）。均衡池而非「按额度上限加权」——网关只报百分比、不报各 key 的额度绝对值，加权无从谈起，均值是可算口径里的最优近似。
- 换来：多 key 网关的圆圈终于回答对的问题——「还剩多少、还能不能用」。图示场景（1% / 93% / 95%）由红色转为黄色（均值 63%，一个 key 已耗尽），池内全部耗尽才转红；单 key、单源供应商的观感一字未变。
