# DR: 字段补全读失败的重试上限

Status: implemented

## Problem

字段补全的盖章规则是"任一候选会话读失败，该项就不写入 `completedFields`，下次启动再试"（[DR: 保存供应商路由键并回填旧用量行](2026-10-28-provider-field-and-backfill.md)）。实测一份数据目录触发了它的死角：16 个候选会话里 5 个的会话日志永久缺失（其中一条还是 `sessionId` 为 `unknown` 的脏行），首轮补全已经把能补的行全部补完（failure 382 行、compaction 9 行等），但死会话永远读不出来，于是每次启动都重扫全部日文件与候选会话日志——既补不上任何新行，也永不结算。现行设计把"绝不放弃任何会话"放在"启动成本"之上，在死会话面前两头落空。

## Decision

`state.json` 新增 `fieldCompletionAttempts`：completer id → 连续失败轮数。每轮补全结束按结果分类结算：

- 无读失败候选（`cleanIds`）：照旧盖章，计数清零。
- 仍有读失败候选（`retriedIds`）：计数 +1；计数达到 `FIELD_COMPLETION_MAX_ATTEMPTS`（3）后照样盖章并清零——死会话视为放弃，不再重试。

判定权从行走层移到状态层：`completeDayFiles` 的返回从 `completedIds`（隐含"无失败才算完成"）改为 `cleanIds` + `retriedIds` 两个事实清单，`markFieldCompletionOutcome` 在一次读改写里完成计数、结算与保留其他 marker。已盖章的 completer 在后续轮次既不计数也不重复盖章。malformed 的计数表读作空。想给已放弃的 completer 重新机会，唯一的路径是手动删掉 `completedFields` 里该项并重启——找回的日志会随新一轮补全生效。

## Alternatives considered

- **记录放弃会话 id 集合，跳过死会话继续补其余。** 放弃：`state.json` 要维护一个随数据增长、语义复杂的名单（会话找回了要不要移出？谁负责清理？）。按轮计数用一个小数字映射达到同样的"停止白扫"目的。
- **比较两轮的失败会话数量，部分找回就重置计数。** 放弃：没有可观察的收益，还要定义"找回"的比较语义。连续失败轮数已经足够表达"死透了"。
- **维持现状，不设上限。** 放弃：实测证明白扫会永远持续，这正是本决策要解决的问题。
- **首轮读失败就盖章。** 放弃：一次网络抖动或文件占用就会永久漏补一整个字段。3 轮预算吸收偶发失败，仍然必然结算。
- **上限设更大（如 10 轮）。** 放弃：每轮之间隔着一次完整启动，3 轮已横跨多次使用会话；更大的上限只是让死会话场景多白扫更久，没有换来可证明的额外安全性。

## Consequences

- 代价：重试预算耗尽后仍读不到的会话，其行永远缺这个字段；日志事后找回也不会自动重补（需手动删 `completedFields` 项触发）。上限对注册表里每个 completer 独立计数，一个字段放弃不影响另一个。放弃发生在第 3 轮跑完时，前两轮的补全结果照常落盘。
- 换来：任何 completer 最多 3 次启动后必然结算，启动补全不再是无限期负债；预算内的暂时性读失败仍有两次免费重试；`state.json` 只增加一个数字映射，其他 marker 写入时原样保留。
