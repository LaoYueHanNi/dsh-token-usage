# DR: 请求池面板的提示语表达会话级对话状态

Status: implemented

## Problem

「最新请求」面板原本只有请求级的提示语：等待首 token、生成中、失败、取消，以及结算后的诊断（未定价、未报告用量、无计时、缓存排除）。面板里最新一条请求已经结算时，右槽常常是空的——用户看不出对话现在走到哪一步了：这一轮已经说完了（没有后续请求），还是模型发起了工具调用、正在等工具结果。两种情况的请求行看起来一模一样（都只是一条已完成的请求），用户只能盯着页面等下一次刷新才分辨得出。

## Decision

部分取代 [DR: 会话用量页的实时请求池与请求级缓存三档提示](2026-10-25-session-request-pool.md) 中页脚只放请求级提示语的规则；请求池的合并、缓存判断与窗口上限不变。

- 会话状态由节点侧的请求观察器按会话跟踪，只用宿主的会话事件事实：`tool/call` 发生而对应的 `tool/result` 未到，即「等待工具结果」（`awaiting-tool`）；`turn/end` 的原因是 `completed` 且没有待返回的工具结果，即「本轮对话已完成」（`turn-complete`）；`llm/retry` 已记录而退避等待尚未结束，即「请求失败，正在重试」（`retrying`，带第几次/共几次、退避时长与失败码）。新一轮 `turn/start` 清掉上一轮的完成结论与重试窗口；`llm/retry-started`（退避结束、下一次尝试即将发出）清掉重试窗口；`turn/end` 同时丢弃本轮未回的工具调用（回合都结束了，那个结果永远不会来）。失败的、取消的、被阻断的回合都**不**算「已完成」。
- 状态经 `fields=session` 响应的 `requestDetails.conversation` 上送，只描述**头条请求（`items[0]`）所属会话**——面板讲的是那一条请求，对话状态就该是同一个会话的。范围内没有结论时字段缺失，不臆造。
- 提示语仍固定在页脚右槽（与左侧费用/缓存读镜像），不另起一行：面板高度继续与请求状态无关。优先级是「会话状态 → 请求自己的生命周期 → 请求自身的诊断」：会话状态说的是「对话现在怎么样」，比单条请求的状态更贴近当下；被压下去的事实不消失——请求自己的提示语与诊断说明整体移进提示语的 Tooltip，信息不丢。
- 客户端只本地化文案（`pool.note.awaitingTool` / `pool.note.turnComplete` / `pool.note.retrying`），状态本身是服务端给的稳定枚举，客户端不推断、不猜测。

## Alternatives considered

- **从会话日志重放推导会话状态** —— 被放弃：日志重放要读盘并重建每一步的工具配对，成本与出错面都远大于实时跟踪；而且面板要的是「现在」，历史日志给不出「正在等工具结果」。
- **用时间间隔猜测「大概在等工具」** —— 被放弃：请求结束到下一条请求开始之间的空档既可能是工具执行，也可能是用户在打字、也可能是网络等待；靠猜会把「本轮已完成」和「正在等工具」混为一谈，正是要消除的歧义。
- **把会话状态放进历史表的某一列** —— 被放弃：历史表是请求的清单，每行一个请求；会话状态不是某一行的属性，塞进某一列会让读者以为它属于那一行。
- **让会话状态独占一行（与上一轮改动相反）** —— 被放弃：会话状态随工具结果到达、下一轮开始而变化，独占一行会让面板高度再次随状态跳变，把下方的历史表顶起又拉回。
- **用「请求失败」行本身表达重试** —— 被放弃：重试是一次**还没发生**的下一次尝试，只有 `llm/retry`（退避开始）与 `llm/retry-started`（退避结束）这对事件能证明它；失败行只能证明过去发生的事，用户看不到系统正在自动恢复。
- **把重试次数与退避时长做进面板正文** —— 被放弃：面板是请求的快照，重试的计数属于「对话正在做什么」，写进请求行会让读者以为这是那条请求的属性；它留在会话状态里，失败码与退避时长进 Tooltip。

## Consequences

- 换来：面板能直接回答「对话现在怎么样」——本轮已结束、正在等工具结果，还是失败后正在自动重试；提示语仍在一行内，面板高度稳定；请求自身的诊断说明一个都没少，只是退到 Tooltip。
- 代价：会话状态依赖插件进程观察到会话事件——插件重启或安装晚于对话开始时没有结论（字段缺失，不显示提示语），这是诚实的「不知道」而不是猜测；观察器多维护每会话的待回工具调用集合与重试窗口（回合结束即清理）。
