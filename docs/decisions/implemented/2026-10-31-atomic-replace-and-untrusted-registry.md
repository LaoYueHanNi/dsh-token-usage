# DR: 本地数据目录的完整性——原子替换、不可信名册与迁移串行化

Status: implemented

## Problem

插件在数据目录里维护两类本地状态：**用量日文件**（`usage-YYYY-MM-DD.jsonl`，唯一的用量原始记录）与**供应商展示名名册**（`providers.json`）。两者都是「读-改-写」型文件，此前各有一条会把用户已有数据写坏的路径：

1. 日文件重写（字段补全回填、reconcile 清理、refile 改期）一律「写临时文件 → `unlink` 目标 → `rename` 临时文件到目标」。`unlink` 与 `rename` 之间若进程崩溃、断电或被强杀，原文件已经删除、新文件还没落地，那一天的用量行全部消失，只剩一个读取端不认的 `.tmp`。Windows 上 `fs.rename` 本身就能覆盖已存在目标（`MoveFileEx` + `REPLACE_EXISTING`），这个 `unlink` 不但多余，恰恰就是丢数据的窗口。
2. 名册读取把「文件不存在」与「文件读不动／JSON 损坏」都当成空索引返回，`upsert` 随即拿这个空索引做读-改-写，把磁盘上其它路由的展示名一并抹掉。展示名**不可从会话日志重建**（日志里只有路由 id），抹掉就只能等用户下次用到该路由时重新捕获，可能永远不回来。这条路径与类注释里「entries already on disk are never deleted by an upsert」的承诺直接矛盾。

两条路径的共同特征是**不崩溃、不报错、界面看不出异常**，受损的只有用户本地的数据文件，而且往往要过一段时间才被发现。

还有第三类，同一个数据目录上的**搬家与写入并发**：数据目录搬家按两阶段提交走（复制 → 切换 → 清理源），判定「源文件已落地」靠的是目标同名文件**大小相同**。而启动链（首跑历史同步 + 随后的同步标记写入）与搬家并发时，标记文件会在复制之后才写进源目录——大小变了，清理阶段便拒绝删除它，源目录永远留着这个文件，`rmdir` 也就不执行，用户看到的是「数据目录搬了一半，旧目录还在」，而且这个状态不会自愈。写一半崩在 rename 之前留下的 `.tmp` 残留是同一类：它不是数据，却足以让源目录非空。

## Decision

**文件替换一律 temp + rename 直接覆盖，不预先删除目标。** 日文件的全部重写路径（字段补全、reconcile、refile）统一走一个 `replaceFile` 辅助：先写同目录临时文件，再 `rename` 覆盖目标；只有当覆盖被文件系统拒绝（`EPERM` / `EEXIST` / `EACCES`）时才降级为「删除目标再改名」。读者要么看到旧文件，要么看到新文件，没有中间的空档。

**读不回的名册不写。** 名册读取区分三种状态：文件不存在 → 空索引（可信，可以写）；读不动或 JSON 损坏 → **不可信**（`null`，不写）。`upsert` 遇到不可信状态就放弃本次写入并记 error，磁盘上原有的内容原封不动。读路径（给界面用的 `read()`）对不可信状态仍返回空索引——界面降级为显示原始路由 id，而不是报错或崩掉。

**名册读加 size+mtime 戳缓存。** 名册只在路由改名时才变，命中率极高；缓存让每请求一次的展示名刷新不再重复读盘解析。写入后主动丢弃缓存，下一次读按新戳重取。

**搬家与启动链串行化。** 启动链（首跑历史同步 + 同步标记写入）作为一个可等待的整体暴露给搬家流程：搬家的排空阶段先等它结束，再复制、再切换、再清理。标记因此必然落在复制**之前**，源目录里的标记与目标里的那份字节相同，清理阶段得以按既有规则删掉它，源目录随之清空。启动链自身在写标记时也以「当前生效的目录」为准（迁移可能已把它换掉），不往已经搬走或正在搬走的目录里写。

**清理阶段顺带清掉本插件的 `.tmp` 残留。** 已落地的文件对应的临时文件（`state.json.tmp`、`usage-*.jsonl.tmp`、`providers.json.tmp` 等）是写入中断的残留，不是数据；它们留着会让源目录非空，进而让「源目录已空」这个前提永远不成立。清理只针对本插件自己写出的临时文件，用户自己的文件一律不动。

## Alternatives considered

- **保留「先 `unlink` 再 `rename`」** —— 放弃：Windows 的 `rename` 本就能覆盖，`unlink` 没有任何必要性，只制造了一个「原文件已删、新文件未落」的崩溃窗口。
- **读失败时用空索引继续写**（原行为） —— 放弃：一次读失败（权限、占用、并发写的半截文件）就会把名册覆盖成只剩本次那一条，其余路由的展示名永久丢失且不可重建。
- **JSON 损坏时视为「不存在」并整份重写** —— 放弃：损坏可能只是并发写导致的截断，磁盘上其实有大部分有效内容；整份重写会把那部分也丢掉。宁可让名册停在「没有名字」这个可用但无损的状态。
- **每次读名册都直接读盘（无缓存）** —— 放弃：展示名刷新挂在每条请求的记账路径上，无缓存时是每请求一次文件读 + 解析；仓库里 `SessionMetaStore` 已有 size+mtime 戳缓存的先例，照抄即可。
- **清理阶段按「大小不同就不删」放宽为「目标存在同名文件就删」** —— 放弃：那会让搬家丢掉源目录里比目标更新的内容，破坏「数据要么在两边、要么只在源」的不变式；正确做法是让写入不与搬家并发，而不是放宽删除规则。
- **搬家不等启动链，靠重试删除源文件** —— 放弃：源文件在复制之后才被写入，内容与目标已经不同，删了会丢掉刚写进去的标记；重试解决不了「内容不同」这件事。

## Consequences

- 换来：日文件重写不再有丢整天数据的窗口；名册在任何读失败下都不会丢名字——最坏情况是界面暂时显示原始路由 id，等名册修好或路由再次被使用即恢复；名册读盘开销从「每请求一次读+解析」降到「每请求一次 stat」；搬家不再与启动链并发，源目录能被真正搬空，「旧目录还在」的半搬状态不再出现。
- 代价：`replaceFile` 多了一层错误分类（覆盖失败才降级），需要按文件系统行为验证；名册损坏时插件不再自动修复它——需要用户或后续写入把文件恢复成合法 JSON 才能重新落名（这是刻意的：宁可不动，也不丢）；搬家现在要等首跑同步结束才动手，用户在刚启动后立刻改数据目录会多等一会儿。
- 记测试：名册「读不回就不覆盖」与「读得回就能覆盖」各有一条用例；日文件的原子替换由既有日文件重写用例覆盖，崩溃窗口本身不入测试（无法稳定构造）；搬家与启动链的串行化由数据目录搬家那组集成用例守住（该组在高负载机器上偶发失败，本决策后连跑三次全量均通过）。
