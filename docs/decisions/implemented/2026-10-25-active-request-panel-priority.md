# DR: 会话请求面板优先展示范围内的活动请求

Status: implemented

## Problem

含子会话范围内，较早启动的子会话仍在生成，而较晚启动的本会话请求已经完成时，严格按开始时间取第一条会让已完成请求占据顶部。活动子请求虽然在历史表内，但用户无法从当前请求面板直接看到它；若期间产生超过 20 条新记录，长请求还会被展示窗口挤出。

## Decision

部分取代 [DR: 会话用量页的实时请求池与请求级缓存三档提示](2026-10-25-session-request-pool.md) 中顶部严格按最新开始时间选择的规则，其余合并、缓存判断与窗口上限不变。

- 服务端在当前范围的全量合并结果中，先按开始时间降序排列，再将最新启动的等待或生成中请求移到第一条，最后截取 20 条；不存在活动请求时，第一条仍是开始时间最新的请求。
- 活动请求刚结算时，观察器保留的实时结算行继续占据顶部至少 1 秒；窗口到期后才按普通历史顺序归入下方列表。仅有落库历史、无法证明刚刚处于活动状态的旧行不触发这段停留。
- 顶部请求结算后，下一次快照自动切换到剩余活动请求中最新启动的一条；全部结束后恢复最新请求。等待与生成中具有相同优先级，不按父子身份偏置。
- 历史表展示剩余最多 19 条，维持开始时间降序，不重复顶部请求。活动总数仍来自当前范围的完整观察快照，不受展示窗口影响。
- 本会话范围不包含子会话；含子会话范围即使没有本会话结算记录，也能展示子会话的活动请求。缓存序列排除在提升面板与截窗之前计算，不能因展示顺序改变冷启动或切换首条的判断。

## Alternatives considered

- **继续严格按开始时间排序** —— 保持时间线简单，但已完成请求会遮住仍在运行的子会话，无法满足当前请求面板的监测用途。
- **只在最近 20 条中查找活动请求** —— 改动更局部，但较早开始的长请求会被新记录挤出，仍会丢失当前运行状态。

## Consequences

- 换来：活动子请求不会被较新的完成记录遮住，多个并发活动请求可以随结算自动交接；保持单一快照契约、范围隔离与最多 20 条的限制。
- 代价：顶部「最新请求」不再总是全局时间最新的一条，而是优先指活动请求中的最新一条；只有下方历史区保持纯时间降序，顶部到历史的整体列表不保证时间单调。
